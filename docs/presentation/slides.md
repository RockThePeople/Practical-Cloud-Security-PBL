# 슬라이드 원고 — Category 3: Kubernetes Audit Log로 SA 오용 탐지

숫자 출처: `evaluation/results/01-baseline.json`, `02-upgrade.json`, `03-describe.json`

---

## 1. 표지
- **제목:** 같은 계정, 다른 의도 — Kubernetes Audit Log로 ServiceAccount 오용 탐지
- **핵심 메시지:** Audit Log만으로 정상과 공격을 가를 수 있는가, 그리고 기본 규칙의 한계를 어떻게 보완했는가
- **화면:** 제목, 부제 "실무클라우드보안 PBL · Category 3", 팀/이름, 날짜

---

## 2. 문제
- **제목:** 같은 SA로 정상과 공격이 섞인다
- **핵심 메시지:** 계정이 같으면 "누가"로는 구분할 수 없다. Audit Log만으로 구분할 수 있을까?
- **화면:**
  - 그림: 왼쪽에 정상 앱, 오른쪽에 공격자. 둘 다 같은 열쇠(SA 토큰 `pbl-crypto-platform-app`)로 같은 문(kube-apiserver)에 들어가고, 문 옆의 기록부(Audit Log)에 같은 이름으로 찍힌다
  - 배경 한 줄: 2025년 암호화폐 플랫폼 침해 사례 — 탈취한 SA 토큰으로 Secret 열거, 다른 workload 접근 시도

---

## 3. 테스트베드와 시나리오
- **제목:** kind 클러스터 + 시나리오 5종 × 5회
- **핵심 메시지:** 같은 SA로 정상 2종, 공격 3종을 각각 5번씩 실행해 25개 실행을 모았다
- **화면:** 표

| 시나리오 | 라벨 | 하는 일 | 요청/회 |
|---|---|---|---|
| normal | 정상 | pods·services·configmaps 조회 | 5 |
| normal_misconfig | 정상 | 위 조회 + 권한 없는 `get secret app-tls` 3회 (설정 실수) | 8 |
| abnormal_1 | 공격 | Secret 목록 열거 | 1 |
| abnormal_2 | 공격 | Pod 목록 → 다른 Pod에 exec 시도 | 2 |
| abnormal_3 | 공격 | pods·secrets·configmaps 반복 열거 (6바퀴) | 18 |

  - 아래 한 줄: SA의 Role은 pods·services·configmaps의 get/list만 허용 → Secret과 exec는 403(거부)
  - 아래 한 줄: normal_misconfig는 "403이면 공격"이 틀리는 경우를 보려고 추가

---

## 4. Audit Log에서 보이는 것과 쓸 수 없는 것
- **제목:** 무엇으로 구분할 것인가
- **핵심 메시지:** IP·UA·속도·토큰은 구분이 안 된다. "무엇을 어떻게 요청했는가"로 구분한다
- **화면:** 좌우 2단 표

| 쓰지 않음 | 근거 (03-describe.json) |
|---|---|
| 출발지 IP | 모든 실행이 `172.19.0.1` |
| User-Agent | 모두 kubectl (abnormal_2 exec 1건만 curl, 공격자가 바꾸기 쉬움) |
| 속도 | abnormal_3 초당 10.3건 < normal 11.4건 |
| 토큰 ID | 정상·공격 모두 실행마다 새로 발급 |

| 씀 |
|---|
| 리소스 (secrets?) · subresource (exec?) · 이름 유무 (list vs 이름 지정 get) |
| 응답 코드 (403) · 허용 목록 (Role 권한) · 시간적 묶음 (30초 / 10초) |

## 5. 기본 탐지 R1~R3
- **제목:** README 관찰점을 그대로 규칙으로
- **핵심 메시지:** 요청 1건씩 보고, 걸리면 모두 high 알림
- **화면:** 표

| 규칙 | 조건 | 대응 시나리오 |
|---|---|---|
| R1 Secret 접근 | resource = secrets | abnormal_1, abnormal_3 |
| R2 다른 workload 진입 | pods의 exec·attach·portforward | abnormal_2 |
| R3 권한 밖 요청 | code 403 또는 decision forbid | 공격 3종 모두 |

  - 아래 한 줄: 사건 묶기 없음 → 알림 1개 = 사건 1개

## 6. 기본 탐지 결과
- **제목:** 공격 실행은 다 잡았지만, 요청 단위로는 절반도 못 잡는다
- **핵심 메시지:** 실행 15/15 탐지, 그러나 recall 0.381, 정상 실행 5/10 오탐
- **화면:** 큰 숫자 4개
  - 공격 실행 탐지 **15/15**
  - 정상 실행 오탐 **5/10**
  - precision **0.727** (TP 40, FP 15)
  - recall **0.381** (TP 40, FN 65)
  - 작은 글씨: TP = 잡은 공격 요청, FP = 잘못 잡은 정상 요청, FN = 놓친 공격 요청

---

## 7. 한계 1: 조각으로만 본다
- **제목:** 공격 흐름 속의 "정상처럼 보이는" 조회를 놓친다
- **핵심 메시지:** 놓친 65건은 전부 공격 중의 평범한 조회이고, 하나의 공격이 사건 12개로 쪼개진다
- **화면:**
  - 그림: abnormal_3 요청 18건을 시간축(약 1.8초)에 점으로 놓는다. secrets 6건만 빨간 점(알림), pods 6건·configmaps 6건은 회색 점(놓침). 빨간 점마다 알림 2개(R1, R3) → 12개
  - 숫자: 놓친 요청 65건 = abnormal_2 `list pods` 5 + abnormal_3 `list pods` 30 + `list configmaps` 30
  - 숫자: abnormal_3 1회당 알림 12개 = 사건 12개

---

## 8. 한계 2: 403이면 무조건 의심
- **제목:** 설정 실수도 공격처럼 high로 울린다
- **핵심 메시지:** normal_misconfig 5회 모두 오탐, 오탐 요청 15건
- **화면:**
  - 정상 실행 오탐 **5/10** — 5회 모두 normal_misconfig
  - 오탐 요청 15건 = `get secrets app-tls` 403 × 3회 × 5실행
  - 비교 그림: "이름을 지정한 get secret app-tls 3번"(설정 실수) vs "이름 없이 list secrets"(열거). 기본 탐지는 둘 다 high

---

## 9. 한계 3: 최소 권한이 깨지면 놓친다
- **제목:** 403이 없으면 R3는 아무것도 못 본다
- **핵심 메시지:** Role이 넓게 잘못 설정되면 공격 요청이 200(성공)으로 찍히고, "거부"에 기댄 규칙은 침묵한다
- **화면:**
  - 개념 그림: 원래 데이터의 `list secrets → 403 forbid`를 반사실 데이터에서 `list secrets → 200 allow`로 바꾸는 화살표
  - 설명 한 줄: 반사실 = 평가 코드 안에서만 403을 200으로 바꾼 사본. 실제 권한은 바꾸지 않았다
  - 숫자: base의 R3 알림 55개 → 0개
  - 주의 한 줄: base 전체 지표는 그대로(recall 0.381). R1·R2는 응답 코드와 무관하기 때문. 이 한계는 보완 탐지기(u12)에서 드러난다 → 11장

- **핵심 메시지:** 한계마다 보완 하나
- **화면:** 표 (severity: low < medium < high, medium 이상만 탐지로 셈)

| 한계 | 보완 | 규칙 |
|---|---|---|
| 1. 조각으로 본다 | 보완 1: 묶기 | C1 열거 패턴(30초 창, medium), C3 정찰 후 exec(10초, high), 사건 묶기(30초) |
| 2. 403 = 의심 | 보완 2: 등급 | R1·R3를 요청 모양으로 등급(이름 지정 get은 low), C2 같은 대상 3회 거부(low) |

## 13. 남는 한계
- **제목:** 1.000은 "이 데이터에 맞췄다"는 뜻이다
- **핵심 메시지:** 같은 데이터로 설계하고 평가했다. 다른 공격 방식에는 열려 있다
- **화면:** 목록
  - 같은 데이터로 설계·평가 → 별도 검증 데이터 없음
  - Secret 이름을 알고 이름 지정 get → low로만 잡힘
  - 허용 목록은 앱이 바뀔 때마다 사람이 갱신
  - 30초보다 느린 열거는 하나로 묶이지 않음 (데이터의 abnormal_3은 약 1.8초라 창 경계를 시험하지 못함)
  - 실제 탈취에서는 정상 앱과 공격자가 같은 토큰·IP
  - R3 단독의 효과는 측정 못 함 (R1·R2와 겹치지 않는 권한 밖 요청이 데이터에 없음)
  - 알림 수는 줄지 않음 (u123 abnormal_3 1회당 19개), 줄어드는 것은 사건 수

## 14. 정리
- **제목:** 정리
- **핵심 메시지:** 같은 계정의 정상과 공격은 IP·UA·속도로는 못 가르지만, "무엇을, 어떤 모양으로, 권한 안에서 요청했는가"를 묶어 보면 Audit Log만으로 가를 수 있다
- **화면:** 한 문장 결론 + 숫자 3개
  - recall 0.381 → 1.000 (보완 1)
  - 정상 실행 오탐 5/10 → 0/10 (보완 2)
  - 권한이 깨진 반사실 recall 0.429 → 1.000 (보완 3)
